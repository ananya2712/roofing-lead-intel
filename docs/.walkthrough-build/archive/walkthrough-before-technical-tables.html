01Project and problem

  • User: a roofing-materials distributor’s sales representative.
  • Problem: decide which contractors to contact and keep track of saved leads.
  • Data: 409 recorded GAF listings near ZIP 10013, within 50 miles: 176 residential + 233 commercial.
  • Scope: explain priority, save leads, update status. Notes and AI insights are deferred.

02Demo sequence

  • 1. Overview: show the pipeline and switch All / Residential / Commercial.
  • 2. Prospects: search, sort, and open a contractor.
  • 3. Details: explain the score and point out unknown information.
  • 4. Save as lead: show the saved row in Saved leads.
  • 5. Take action: mark Contacted; show updated counts and the follow-up queue.
  • Open: http://localhost:3000. Follow-up means Contacted with no status change for 14+ days.

03Tech stack and why

  • Next.js + React + TypeScript: four views, shared controls, typed API calls.
  • Flask + Pydantic: Python business logic with validated API inputs and responses.
  • PostgreSQL + SQLAlchemy: related records, persistent status, database-enforced uniqueness.
  • Docker Compose: runs the UI, API, and database together.
  • Trade-off: separate UI/API services need more setup than one framework; business logic stays in Python.

04Functional and non-functional requirements

Functional

  • Search/filter contractors and explain their priority.
  • Save a company once; change its lead status.
  • Show first-contact and follow-up work queues.

Quality

  • Repeatable scoring; missing information stays Unknown.
  • Validate requests; prevent duplicate saved records.
  • Show loading/errors and preserve saved work.

05Data flow

  • Setup: GAF browser collection → JSON snapshots → flask import-snapshot → validated prospects + stored scores.
  • Save: button → POST → insert lead → commit → return updated details. No live GAF or AI request runs.

06Database model

  • Separate ownership: source facts, calculated priority, and representative work.
  • PK = primary key. FK = foreign key to prospects.id. Each prospect has at most one score and one saved lead.
  • Duplicate protection: unique listing ID per directory; unique saved prospect; unique non-null company phone key.

  • Prospect inputs: search, directory, priority, distance, certification, sort, page.
  • Lead inputs: directory, active/all/dismissed scope, status, first-contact/follow-up queue, sort, page.
  • Status body: {"status":"contacted"}; allowed: New, Contacted, Qualified, Dismissed.
  • Errors: 422 invalid input; 404 missing record; 409 company already saved through another listing.
  • Directory counts: follow the selected directory; saved-lead totals precede other table filters. No authentication is implemented.

08Frontend behavior

  • Views: Overview, Prospects, Prospect details, Saved leads.
  • Saved leads: first-contact/follow-up queues, status cards, matching count, reasons, distance, and contact actions.
  • State: filters live in the URL; useLoad guards older responses; save/status controls show pending and error states.
  • Small screens: compact saved-lead cards replace the desktop table.

09Key decisions and challenges

  • Fixed scoring over AI: distance 35 + product fit 35 + data readiness 30. High ≥70; Medium 45–69. Ratings/reviews do not score.
  • Example: 35 distance + 20 certification + 10 systems + 0 specialty + 30 readiness = 95. This measures fit under rules, not buying intent.
  • Snapshots over live scraping: recorded GAF data avoids runtime scraping; refreshing data requires another import.
  • Phone-based company matching: prevents known duplicates across directories; missing/shared numbers remain a limit.
  • Database constraints over UI-only checks: enforce uniqueness during competing saves. Repeating a save returns the existing lead.
  • After the MVP: authentication, safe schema upgrades, and backups before shared production use.
